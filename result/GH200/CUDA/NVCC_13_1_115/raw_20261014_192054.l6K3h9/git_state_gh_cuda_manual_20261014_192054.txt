-CUDA uses explicit runtime calls instead of directive-based target/data regions, so not every method is a literal translation. The CUDA backend keeps the same measurement driver and method numbering, but maps the API ideas as follows:
-
-| Method | CUDA form | Relationship to OpenMP/OpenACC |
-|--------|-----------|--------------------------------|
-| 0 | one scalar kernel launch | Directly comparable launch baseline |
-| 1 | `cudaMalloc + H2D + kernel + D2H + cudaFree` | Mimics `map(tofrom)` / `copy` lifecycle |
-| 2 | `cudaMalloc + H2D + kernel + cudaFree` | Mimics `map(to)` / `copyin` lifecycle |
-| 3 | `cudaMalloc + kernel + D2H + cudaFree` | Mimics `map(from)` / `copyout` lifecycle |
-| 4 | `cudaMalloc + kernel + cudaFree` | Mimics `map(alloc)` / `create` lifecycle |
-| 5 | one scalar action per CUDA block | Mimics teams/gangs scalar launch |
-| 6 | grid-stride loop kernel | Direct CUDA equivalent of parallel loop worksharing |
-| 7 | stream launch plus stream synchronize | Mimics async launch followed by wait |
-| 8 | grid-stride loop with `atomicAdd` | Direct CUDA atomic analogue |
-| 9 | shared-memory block reduction plus final atomic add | CUDA-style reduction analogue |
-| 10 | explicit `block_count` and `thread_count` launch | Direct CUDA launch-shape measurement |
-| 11 | repeated explicit block/thread launch work, with `N` as repetition count | Mimics repeated inner parallel/worker work |
-
-Methods 0, 6, 7, 8, 10, and 11 are the cleanest CUDA counterparts. Methods 1-4 are comparable by intent rather than syntax because CUDA exposes allocation and copy operations explicitly. Method 9 is also comparable by intent, but the implementation must use CUDA reduction mechanics rather than a directive-level reduction clause.

+flags, default schedules, dynamic-thread setting and parallel directives are not

+|--------|-------------------------|
+| 0 | One scalar kernel; resident data |
+| 1 | Allocation, H2D, scalar kernel, D2H, release per repetition |
+| 2 | Allocation, H2D, scalar kernel, release per repetition |

+Original method 6 requests teams and a thread limit, without specifying either
+schedule. Original methods 8/9 do not use the CLI team/thread controls. Methods
+10/11 also rely on the runtime's actual parallel thread count. Consequently, CUDA
+cannot infer unique participant counts or iteration owners from those clauses.
+Without a profile it uses an explicit cyclic CUDA schedule, labelled
+`cuda_static_cyclic_unverified`; it is not advertised as verified OpenMP ownership.
+
+`OpenMPProfile=<csv>` or `CUDA_OPENMP_PROFILE=<csv>` makes CUDA replay observed
+OpenMP team/thread counts and per-index owners for the exact method/N/workload/
+requested-controls key. Requested counts remain distinct from actual counts in
+index calculations and device CSV metadata. Invalid, missing, conflicting or
+nonuniform profiles are rejected. The diagnostic records one repetition of delay
+calls. Chunk boundaries are inferred from contiguous team-owner runs and ordering
+within each thread is inferred from increasing indices: the profile does **not**
+record OpenMP parallel-region events. Its mode is
+`observed_owners_inferred_chunks`; complete synchronization equivalence still
+requires device validation, not an assertion that the defaults are known.
+
+Generate an observational copy and capture the original OpenMP behaviour on GH200
+without editing its production source or forcing its runtime settings:

+```bash

+The last six arguments are requested teams, thread limit, N, MAX_ITER,
+MAX_ARRAY_SIZE and method (`-1` captures all twelve). Match the driver's **printed**
+workload values: it may enlarge MAX_ITER/MAX_ARRAY_SIZE. Different workload keys
+need their own observations. Trace writes perturb execution and are correctness
+diagnostics, not timing measurements. Empty workloads have unobserved participants
+and cannot provide a replay profile.
+
+The observational copy records team/thread information directly at the original
+delay call sites. The production delay function, loop nesting, parallel clauses
+and scheduling controls stay unchanged. No extra device observer function queries
+the OpenMP execution context; the earlier version hit an invalid shared-memory
+read in that function on GH200 with NVHPC 26.3.
+
+For resident-data methods, CUDA transfers `a` and zeroed `tmp` before timing and
+copies both back afterwards. Host increments and device buffers remain separate.
+Original OpenMP memory-mode flags are preserved; inspect the intended platform's
+mapping behaviour rather than silently forcing a different memory mode.
+Method 3 leaves unwritten copyout elements unspecified in both APIs.
+
+Method 9 is an array reduction again. Thread-private N-element buckets are cleared
+for each CUDA chunk, merged into team-private buckets across chunks, then merged
+into `tmp`. `tmp` accumulates across repetitions. Merge-before/merge-after barriers
+protect the scratch lifetime; method 11 has a team-local join after each of its N
+phases. OpenMP leaves its physical reduction tree unspecified. CUDA scratch uses
+`actual_blocks * (actual_threads + 1) * N` doubles outside the timer; private
+initialisation and merging execute inside the kernel.
+OpenACC method 9 also retains parallel array-reduction work, implemented explicitly
+because [NVHPC lists subarray reduction clauses as unsupported](https://docs.nvidia.com/hpc-sdk/compilers/hpc-compilers-user-guide/index.html).
+
+Optional device timing is a **second pass after all original host samples and BIC
+calculations finish**. It profiles a private host-array clone and writes
+`cuda_device_times.csv`; `raw_times.csv` keeps its original schema and host timing
+protocol. The uninstrumented host pass creates or records no CUDA events.
+
+Each inner repetition uses these monitoring points, on the same kernel stream:
+
+```text
+allocation / required H2D
+record start event
+launch kernel
+record stop event
+original device/stream wait
+required D2H / release
+```
+
+The stop event is submitted immediately after the launch and before waiting.
+Copies, allocations, profile uploads, frees, host increments and result-file writes
+are outside the event pair. Method 7 records both events in its own stream.
+Method 9 includes private initialisation, atomic/reduction work and merges;
+method 11 includes all N phases and their joins. The mean of separate per-kernel
+event intervals is reported in microseconds, not an event spanning the entire host
+repetition loop. Events measure a GPU stream interval, including device scheduling
+or idle time between timestamps; they are not a pure GPU-instruction timer.
+See [CUDA event timing semantics](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__EVENT.html).
+Do not obtain host launch cost by subtracting independent-pass device samples from
+host samples that include mapping/copies.
